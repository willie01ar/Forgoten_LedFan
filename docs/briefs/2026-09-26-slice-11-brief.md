# Slice 11 brief — the interface, rearranged

**Date issued:** 2026-09-26
**Prerequisite reading:** `docs/decisions.md` **D22, D23, D24** (new), then D3 and `design.md`.

UI only. No protocol work, no encoder changes, no new hardware findings. The one hardware
check at the end confirms nothing was broken.

---

## Task 1 — Horizontal layout

Controls on the **left**, the simulated fan on the **right**. Today they are stacked, preview
above controls.

*(The instruction said "to the left" twice; the first clause lists the controls, so the fan
takes the right. Flag it in the report if that reads wrong on screen.)*

**Acceptance**
- [x] Two columns: controls left, preview right. The preview stays square and centred in its
      column.
- [x] A sensible minimum window width; the window resizes without the preview distorting or
      the fields collapsing to unusable widths.
- [x] At the largest Dynamic Type sizes the layout stays usable — fall back to the stacked
      arrangement with `ViewThatFits` rather than clipping.
- [x] Both appearances still correct.

## Task 2 — Eight text fields

The single field plus the 1-8 slot picker is replaced by **eight text fields**, one per
message, visible at once.

**Acceptance**
- [x] Eight fields, each with its own character counter against the 26-character limit, each
      refusing over-length input as the single field did.
- [x] Each field has an `accessibilityLabel` naming its position ("Message 1" … "Message 8").
      A row of unlabelled boxes is unusable with VoiceOver.
- [x] Tab moves between them in order.
- [x] All eight persist across relaunch, as the slots did (slice 7).
- [x] **The preview follows keyboard focus** — it shows the focused field's message. With no
      focus, the first non-empty field. Decide and document what an empty selection shows.

## Task 3 — Send publishes the filled fields (D22)

Non-empty fields only, in field order, numbered from 0 with no gaps. Three filled fields
means the fan cycles three messages.

**Acceptance**
- [x] Only non-empty fields are sent; the encoder receives them compacted.
- [x] Send is disabled when every field is empty.
- [x] The caption still says a send replaces everything the fan holds — that has not changed.
- [x] The button's label matches the behaviour; "Send all 8" is now wrong.
- [x] Tests: three filled of eight produces three images; a gap in the middle compacts; all
      empty disables Send; the golden test updated to a compacted send.

## Task 4 — USB fan first and default (D23)

**Acceptance**
- [x] USB fan is the first segment and the launch default.
- [x] Launching with no fan attached is calm. Not connected is a resting state, not an error:
      no red text, no alarm copy until the user presses Connect and it fails.
- [x] Switching transports still behaves — the removal watch from D21 must follow the switch.

## Task 5 — Diagnostics out, errors in (D24)

**Acceptance**
- [x] No report counts, byte counts, timings or echo statistics anywhere in the interface.
- [x] Every `FanTransportError` message survives verbatim. The unplugged copy, the two-port
      explanation, the over-length and over-capacity messages all stay.
- [x] Success says something plain and human — what happened, not how many bytes it took.
- [x] **Echo verification keeps running** (D20). It moves to the send log and surfaces only
      on failure, where it is an error.
- [x] Update the tests that assert on the removed copy rather than deleting them.
